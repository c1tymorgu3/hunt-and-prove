# Delegating work to subagents

Children buy parallelism and context isolation, not judgement. They inherit the same model, cannot ask questions, and only their final summary comes back — so the whole craft is scoping, ownership, and machine-checkable acceptance.

## When to Use
- A task splits into pieces that touch different files or different systems.
- You need long running scrapes/builds/tests off the main thread.
- A research question needs many independent lookups.

## Procedure
0. **Settle the approach before you fan out.** When the ask has more than one credible shape — build it vs adopt an existing tool, which provider, which UI base, which data source — put 2-4 concrete options to the user and let them pick. Starting to build a whole subsystem on an unstated assumption reads as ignoring them and costs a throwaway pass; once the direction is chosen, execute end-to-end without further check-ins.
1. **Split by file, not by ambition, and size the deadline to the task class.** Every child gets one deliverable and an explicit deadline in the brief ("finish within N minutes, a partial result is acceptable, report the real number"), never one number applied to everything. Rough calibration: recon, probing, and single-endpoint tests finish in 20-25 minutes; a full APK decompile, a source-code audit, or anything that must download a large artifact needs 30-45. A child with no deadline spends 20 minutes tuning one subsystem and hands back nothing; a child given 20 minutes for a 45-minute decompile hands back a truncated file and calls it done. When a task's floor is dominated by a download or install, the parent does that part first and passes the path (see step 9) instead of inflating every child's budget.
2. **Write the ownership map into every task.** Name the exact files the child owns and the exact files it must not touch, and repeat it in siblings' contexts — children do not see each other's briefs.
3. **Fix the interface before dispatching.** When two children must meet, define the exported symbol and its signature in both contexts (`LIVE_TOOL_DEFS` + `runLiveTool(name, args)`), and have the consumer import it optionally with `try/catch` so a missing file degrades instead of breaking the build.
4. **Order the instructions: write, then verify.** "Explore first, then implement" burns the budget on reading. Say explicitly: write the file, then run the acceptance command, then iterate.
5. **State acceptance as a command plus expected output.** `npx impeccable detect <url>` must print 0 anti-patterns; `npm run build` must exit 0 and list route X; the endpoint must return HTTP 200 with N rows. Anything softer comes back as "done" with no evidence.
6. **Demand evidence, not narrative.** Require the real command output, row counts, and paths in the final message. Self-reported success from a child is a claim that still needs your spot-check for external side effects.
7. **Keep one owner per shared resource.** Build, dev server, database file, and lockfiles get exactly one writer; every other child reads. Concurrent `next build` + server restarts serve stale chunk hashes and render an unstyled page that looks like a design failure.
8. **Prefer one batched `delegate_task` call** for related subtasks: their completions arrive together and you get one consolidated result instead of interleaved ones.
9. **Hand the child the artifact, not the recipe to obtain it.** Anything that needed a human — a solved captcha, an authenticated session, a downloaded binary, an installed toolchain — gets obtained once in the parent and passed in as an absolute path plus a one-line working invocation. Children cannot answer a prompt, click a checkbox, or ask the user, so a brief that says "download it" produces a full budget spent on dead mirrors and a zero. The brief should name the artifact's path and say "do not re-download".
10. **For a long fan-out, give children a shared findings directory and put a cron reporter over it.** Each child writes its own `<target>/<id>.md` and appends nothing to its siblings' files; a recurring job reads that directory (and the live transcripts) and posts status. The parent stays free to steer, and the user gets periodic progress without the parent polling transcripts between turns. When the user wants to watch rather than read digests, a local dashboard beats the cron report: read `~/AppData/Local/hermes/cache/delegation/live/*/manifest.json` for the goals and each `task-N.log`'s mtime for liveness, serve it on a fixed port, and give it two views — columns of agents, and a graph linking each hunter to its refuters — with status dots for active, idle and stalled. It is the same data the cron job reads, at a glance instead of prose.
11. **Children cannot see each other, so share a board rather than a conversation.** Two children dispatched in the same batch have separate contexts and separate terminals, know nothing of one another, and cannot call `delegate_task` themselves — a mesh is not available, and simulating one wastes tokens. The cheap substitute is a single append-only `SHARED.md` at the fan-out root plus a steer to every child: read it before your next phase, append one line per verified fact (`- [ID] target — what — VERIFIED|DEAD`), and do not re-test a path a sibling marked DEAD. Facts only; a board that collects prose becomes the noise it was meant to remove. You remain the router: transcribe a finished child's key findings into the board yourself before the next wave, because a child that ends early may never have written its lines. When you deliberately give several children the *same* brief — three agents hunting one class of bug — put a claim table at the top of the board instead of a prose log: `| surface | owner | status |`, with the instruction "claim a row and write your name before starting; do not take a claimed row; if all rows are taken, add a new one". Identical briefs otherwise converge on the most obvious file and you pay three times for one pass.
12. **Keep the fan-out saturated, and use a scout-then-pair handoff.** A child that finishes is capacity sitting idle: when one returns, dispatch its replacement in the same turn rather than waiting for the user to ask. For open-ended discovery work the pattern that holds up is one child whose only job is to pick the next target against written criteria, then two children working that target in parallel once it returns — the scout's output has to be a decision with a reason, not a list, or the pair re-litigates the choice. Give the scout the exclusion list of everything already tried so it does not re-propose dead targets, and have it report the criteria it scored against so you can defend the pick.
13. **When one finding is worth the whole fan-out, split it by role, not by idea.** A single candidate that decides the outcome (the bug about to be submitted, the fix about to ship) is served better by eight narrow jobs than by eight opinions. The split that works on a code bug: (a) build with sanitizers and hand every sibling the binary path, (b) reachability — trace the untrusted input to the defect and answer remote vs local-only, (c) minimal reproduction with the smallest input that still triggers, (d) consequence of the memory access — crash only, or genuine over-read, (e) impact and escalation against the program's own severity model, (f) exclusions plus the exact category to file under, (g) **independent verification by an adversary**, (h) the report, written only from what (a)–(f) actually produced. Role (g) is not optional: its whole job is to reproduce from a fresh copy and try to invalidate the harness, and it is the one that catches the team having proved something no real input can cause. Tell every role to write to its own file under `teamA/` or `teamB/`, and tell the report author explicitly to downgrade itself honestly when reachability, consequence or exclusions come back negative rather than filling the gap with prose.

    When the whole attack surface of a target has to be covered instead of one already-chosen finding, invert the split into hunters and refuters and read `references/prove-refute-swarm.md`: gate the hypotheses first, then five hunters with one vector each and five refuters with one permanent rebuttal job each, and apply the survival test that ends most claims before they reach a triager.
14. **Split the scouts by pool, not by criteria, when the question is "which target next".** Two or three children searching *disjoint pools* cost the same wall-clock as one searching everything and cover three times the ground: one takes artefact type A (native daemons and CLIs), one B (high-paying protocol or crypto code), one C (multi-tenant web with email-only signup). Give each the same written requirements and the same list of already-burned targets, and require three things back: a scored top three against those requirements, **one** recommendation with the exact command that builds or runs the thing, and three named hypotheses for the hunter team to start from. The hypotheses are what makes the handoff worth it — the next wave begins from named vectors instead of redoing the recon. Score runnability before reward: the winning target is the one whose artefact can actually be executed and whose attacker is a party without the capability, not the one with the largest payout band. A pool where every candidate fails one requirement is a valid answer, and the scout should say which requirement and what the closest miss was.

## Pitfalls
- **A child cannot pass an interactive gate.** Captcha interstitials, login walls, 2FA prompts, EULA dialogs and "click install" screens all end the same way: the child loops, reports a blocker, and returns nothing usable. If the brief touches one, the parent resolves it first — or the child gets an explicit "if you hit X, stop and report it, do not retry" instruction so the budget survives. **Registration eligibility is the same class of gate with one difference: the parent usually cannot resolve it either.** When a task's authenticated surface sits behind a signup that wants a mobile number, a national identifier, a bank relationship or a document upload, no child and no steer gets past it — so make that question a ten-minute probe before the fan-out, require the answer as the first line of its report (`ACCESS-OK` or `ACCESS-BLOCKED - reason`), and when it comes back blocked, re-scope the whole batch to what needs no session instead of dispatching four more children at the same wall.
- **A child's severity or confidence label is a guess.** Children triage without the exclusion list, the program policy, or the user's risk tolerance in front of it. When a child's result is about to become a recommendation to the user (submit this, ship this, pay for this), re-verify the top item yourself before repeating the label.
- **A fix brief can delete the thing the user liked.** When a child is told to make something "cleaner, bigger, centred", it will rebuild the layout and quietly drop the structural feature that carried the value — a dense web of edges becomes a tidy grid, a live view becomes a static list — and the user's next message is "you destroyed it". Any re-tasking of work the user has already praised must state the property as a hard constraint ("keep the crossing edge web; keep the live pulse") and ask for a **count** in the summary (number of edges rendered, number of nodes) so "I improved it" cannot hide a removal. Steering a running child with the same constraint works if it has not yet written the final file; otherwise re-dispatch.
- **A child's claim about runtime behaviour is a hypothesis until a sibling has executed it.** Static reading produces confident false positives: a state variable that looks unmaintained because the update is three lines above the loop, a branch that looks missing because it lives in a macro. Before a finding goes to the user, someone must have compiled or run it and kept the output; assign that as its own job instead of trusting the same child to police itself, and have the verifier check the harness too — whether it went through the real parser or hand-built a structure no caller could send.
- **Two children reporting the same finding mean the split was wrong, not that the finding is certain.** Repetition feels like confirmation and is usually convergence on the most obvious file. Treat a duplicate as a signal to re-scope by role (build, reachability, consequence, impact, verification) rather than to raise your confidence.
- **A child that hangs on a heavy tool call dies with the tool.** Screenshot-and-analyse loops inside a child (`vision_analyze` on a full-page PNG) can stall past a minute and take the whole child down; hand visual work deterministic gates instead — a design detector CLI, `getComputedStyle` probes, HTTP status and row counts — and take screenshots only for the human.
- **Finished children cannot be steered.** `action='steer'` fails with "no live subagent" once the child exited; check `action='list'` before steering, and re-dispatch instead of retrying.
- **Interrupted children leave usable artifacts.** Before re-running anything, list the files they were told to write — often most of the code landed and only the verification plus one page is missing. Finishing in the main session is usually faster than a second fan-out.
- **Steering must arrive mid-run.** Queued text lands on the child's next tool result; a correction sent in the last seconds is reported back as `missed_steer`.
- **Do not outsource judgement calls.** A child cannot ask the user anything, so taste, product direction, and "is this good enough" stay with you; children implement and measure against a spec you wrote.
- **A child's background processes are killed with it.** Harvesters, dev servers
  and log tails it started die at completion, so anything that must outlive the
  child belongs to you: re-launch it after the batch, and keep long-running
  refreshers out of child scopes entirely.
- **A fan-out of compilers starves the machine the user is working on.** Several children each running Maven, Go, `dotnet test` or a bundler saturate every core, and the user experiences it as frame drops in whatever they are doing, not as agents running slowly. Do not kill the builds — that throws away the evidence the fan-out exists to produce. Drop the heavy processes to Idle priority instead (`Get-Process java -ErrorAction SilentlyContinue | ForEach-Object { $_.PriorityClass = 'Idle' }`), name the culprit and the interpreter it runs under, and give the remaining time from the batch's own budgets. Offer to kill them only if the user says it is still felt.
- **Repeated identical scopes fail identically.** If two runs of the same task both get cut, the third run needs a smaller scope, not more retries.
- **Children research past the constraint you forgot to state.** A child told to "find better sources" will survey paid tiers, signups and pricing when the user only wanted free ones. Put the constraint in the brief (free only, no accounts, no cards, which dimension matters) and steer it back the moment the transcript shows scope creep.
- **A deadline steer must also lower the bar.** Pair "finish in N minutes" with "a partial result is acceptable, report the true number" — otherwise the child keeps chasing the original acceptance criterion and lands with nothing.
- **Read the transcript, not the clock, when the user asks for status.** `action='list'` gives elapsed time only; a few lines of the child's transcript tell you whether it is measuring, looping, or stuck, so you can answer with what it is doing instead of "still running".
- **Measure idleness before punishing it.** Asked to "stop them slacking", audit first: last timestamp per child against now, tool-call count, the most-repeated command signature (a real loop repeats one identical command far more than the rest; ordinary iteration varies the arguments), and whether the promised output file exists. Children whose last timestamps all sit within seconds of each other are working, and saying so beats a theatrical steer that changes nothing. `scripts/audit_agents.py` prints that table for every child in a fan-out. When a steer is warranted, make it a wrap-up: name the strongest lead already found, forbid new discovery, and lower the bar to "partial is fine, report the real number".
- **A child keeps polishing after its acceptance test passed.** When the transcript shows functional evidence (endpoints 200, build clean) and it has moved on to screenshots, contrast tweaks or lint nitpicks, send a wrap-up steer that names the evidence already collected and asks for the final report plus cleanup (close its test server). Left alone it burns another 20 minutes and reports late.

## Reporting back
Collapse results into what changed, what was verified with which command, and what remains — per unit, not per child transcript. When a child's claim matters (deployed, uploaded, published), verify the artifact yourself before repeating it.

While children run, post a one-line status at every phase boundary (dispatched → first measurement → result). A user who sits through ten silent minutes starts asking "durum ne" and reads the silence as a stall; one line naming what each child is doing right now is enough. Do not narrate tool calls, and never promise a result you have not measured.
