# Bug bounty hunting

The work is finding a defect that survives the team's own model of their product, proving it with something that executes, and filing it against an asset the brief actually lists. Breadth of scanning is not the variable; depth on one surface is. A report that a triager cannot argue with comes from reading their code and their exclusions before touching their hosts.

## When to Use
- Authorized bug bounty / VDP work (HackerOne, Bugcrowd, Intigriti).
- Judging whether a program is worth the effort before spending agents on it.
- Any task where an agent must test a live target and report findings.

## Non-negotiables
1. **Extract the scope first, from the API, not from a screenshot.** Only listed assets get traffic. One request to an unlisted host can void the submission and gets you banned.
2. **Read the exclusion list before testing.** Typical killers: business logic and misconfiguration out of scope; plain open redirect / clickjacking / self-XSS / missing headers / rate-limit-on-non-auth out of scope; "full compromise only" programs reject everything else. HackerOne's **Core Ineligible Findings** list is the gate most programs import wholesale: software version / banner disclosure, descriptive error messages and headers, missing security headers, SSL/TLS best-practice gaps, open redirect without demonstrated impact, self-XSS, CSRF on unauthenticated forms, rate limiting on non-auth endpoints. Anything on that list is worth $0 however clean the evidence, so check a candidate against it *before* writing the report.
3. **Never exploit for real.** Prove reachability with the minimum request, then stop. No data modification, no other users' data, no DoS, no brute force, no account creation without the user's explicit approval.
4. **No automated scanners on live bounty targets.** They generate noise, break rate limits, and triagers treat their output as unverified. Write small targeted scripts.
5. **Rate limit yourself to ~1 req/sec.** Every agent adds up.
6. **Identity header.** If the program supports it, send a custom `User-Agent`/header with the researcher handle so the SOC can distinguish you from an attacker.
7. **Credentials and one-time codes are the user's to type.** Drive an authenticated session as far as email/OAuth will take it, then hand the phone/SMS/password step to the user in the browser window and continue from the resulting session. Never ask for an OTP or password in chat and never type one — a session you built that way is not attributable and not defensible.

## Pre-flight — Can this account submit anything?

Run this before picking a program, before scoping a target, and before spending an agent on anything. It is the cheapest check in the workflow and the most expensive one to skip, because a session's findings are worthless if the account cannot file them.

- Read the account's **trial-report balance and Signal status** (Settings > Rewards and Payments, or any program's submission page). Three trial reports are shared across every program whose Signal requirement the account does not meet, and a fresh account usually does not meet even `0.0` because its Signal is still being computed.
- **Every open program on the platform carries a requirement.** Measured across all 371 bounty programs: 220 are open and all 220 are gated, the modal value being `0.0`; the only ungated programs were paused or disabled. VDPs are not an escape either — 232 open VDPs, all gated. So an account sitting at zero trial reports cannot submit anywhere until one of its reports is triaged or resolved, or 90 days pass.
- When the balance is zero, the honest options are: wait for a pending report to be triaged, move to a platform whose gate you can meet, or write the finding up properly and hold it. Choose one of those openly instead of discovering the gate at submission time. Bugcrowd is the measured escape: 296 engagements, every one open to a brand-new account, with scope, reward table, average payout and validation window readable logged out — endpoints and the filter chain that narrows them are in `references/bugcrowd-platform.md`. Bugcrowd's own new-account cap is six submissions per seven days and is lifted by accuracy, not by time; when it is spent, the platforms that still accept a report are **audit contests** (Code4rena, Sherlock, Cantina, CodeHawks — fixed scope, no cap, no triager to call a real defect informational, and the best fit for a read-and-prove swarm), **Immunefi** (code-based, no submission cap, identity verification only at payout, evidence is a Foundry test against the deployed code) and **YesWeHack** (open registration, public programs from $50). Vendor-run programs (Google, Microsoft, Meta, Apple, Mozilla) have no cap either but a much higher bar. huntr is no longer the open-source platform it was: it is an AI/ML challenge site now. Which one to pick, and the rule that a payout floor must never be a filter: `references/platform-selection.md`.
- **The priority a triager assigns to your duplicate is the cheapest severity estimate you will ever get.** Points only follow a duplicate when the original is P1 or P2 and reaches a final state, so a duplicate usually pays nothing — but its rating prices the class. A mass-assignment finding we reached by reading a vendor's recent authorisation fixes came back duplicate at P3, which told us the class pays $500 and that the codebase has more of it; that is worth more than the $0 the report earned.
- **Never open a second account on the same platform to get around the gate.** Platforms call that account collusion and answer it with a permanent ban, so it is not a workaround.

## Phase 0 — Is this program worth it?

Pull the numbers before anything else. Rank by **acceptance economics**, never by max bounty:

- **Time to triage is the first filter, not the reward size.** A team that triages in months gives you almost no feedback, and without feedback you cannot tell a wrong model of the product from a slow queue. Prefer a team that answers within days even when its ceiling is lower; treat a ten-month queue as an archive, not a workspace. Reject anything over 14 days. Response efficiency is not speed: 100% efficiency in an 11-month queue is still an 11-month queue, and "last resolved 4 days ago" describes one report, not the queue.
- Readings the program page highlights block: HackerOne lays it out **value above its label**, so the number sitting above `Average time to triage` is the triage time. Read one program you know the answer for before trusting your parse on the others.

- `awarded_reports / awarded_reporters` — how farmable it already is.
- **Response efficiency** (below 80% = reports die in triage) says whether they answer at all, not how fast. The only speed metrics are `Average time to triage` and `Average time to bounty`; a program at ten months to triage gives you no usable feedback loop, so read both before committing a night to it, and weight triage time heavily when the objective is a first accepted report rather than a first finding — `references/hackerone-platform.md` covers how to read them without misreading the labels.
- **Reports received (90d) vs resolved** — 4000 reports and 3 resolutions is a wall.
- **Per-asset resolved-report counts are the clearest map of what a team accepts.** The scope table breaks resolved reports down per asset. A program whose acceptances concentrate on one anonymous host is telling you which host is worth reading; a repo with zero resolved reports is telling you it is unexamined; a program where every resolved report sits on an authenticated surface is telling you where its boundary actually is. Read the distribution before picking an asset, not just the program total.
- **Entry gates**: Signal requirement, ID verification, invite-only, trial-report limits. A Signal 3.0 gate means a fresh account cannot realistically compete. How Signal, trial reports and payouts actually work: `references/hackerone-platform.md`.
- **Region gate on account creation.** Before planning any authenticated testing, confirm the product will register a user from the researcher's country. Consumer apps are frequently geo-fenced at signup: a Turkish phone number on a US-only delivery app comes back `400` from the provider-link endpoint with `country_iso_code` echoed in the body, and no amount of recon fixes it. Check the signup form's country selector or the provider-link response *first*; if the region is closed, the authenticated surface is gone and the program's remaining value is mobile/source-code only. Never ask the user for an SMS code to work around this — the blocker is the country, not the number.
- **Asset testability with what you have**: source code and mobile APKs need no live session and no browser, and are never behind a WAF. Live web apps behind Cloudflare cost a human-solved challenge before the first request (see `references/waf-walled-targets.md`) — factor that in when ranking.

**Three gates decide whether a target can pay at all, and each is cheaper to check before the fan-out than after.** (1) *Can you run the artefact?* Build the binary, fork the chain, stand the service up. A class you cannot execute stays a HYPOTHESIS and dies in triage, so a program whose product only runs on infrastructure you do not have is not a source-code target however good the repo looks. (2) *Does the brief pre-answer your classes?* An exclusion list, or a published security model, that already names the classes you would find is a trap: one program had written down that it would not pay for almost everything the code contained, and we found it anyway. (3) *Does the brief name a closed list of acceptable outcomes?* A five-item eligible-outcome list silently excludes standalone parsing and memory-safety bugs even when the repo is full of them. Read the list and confirm your best class is inside it before committing agents; a closed list is a filter to aim at, not a wall, but only if you aim.

**The fourth gate is access, and it is the cheapest one to check and the one that kills a whole program.** Before any agent touches an authenticated surface, read the signup form and answer what registration demands: an email only, or a local mobile number, a national tax or insurance identifier, a local bank relationship, a document upload. A consumer finance app whose signup wants a national insurance number and a domestic direct debit is closed to us no matter how good the code is, and the same is true of any product that verifies identity before it will show a session. Make this a ten-minute job for one agent with a required first line of `ACCESS-OK` or `ACCESS-BLOCKED - reason`; if it is blocked, the program's remaining value is its source code or its mobile binary and nothing else, so say that before the other four agents start.

**A brief that provisions a test instance or a sandbox deletes the first gate outright.** Some programs hand you a throwaway deployment (`bugcrowd-<your-own-instance>.<vendor>.cloud`), a timebomb licence, or a hosted sandbox; that turns "can we run the product" from an infrastructure project into a signup, and it is the single strongest signal that a runtime proof is achievable tonight. Search the brief's description and `additionalInformation` for `sandbox`, `your own instance`, `trial`, `evaluation` and `self-host` before ranking by payout, and prefer a $300 program you can execute over a $25,000 one you can only read.

**Choose programs with visible recent acceptances, not programs nobody has touched.** An empty queue reads like opportunity and is more often the signature of hardened code: six low-competition targets in one night produced twelve genuine defects and zero acceptances. A program with several accepted reports in the last ninety days tells you two things at once — the class of bug exists there and the team engages — so start from its recent acceptances, read which components they touched, and work the adjacent component those reports did not cover.

**Read the age of the listing before reading its emptiness.** An empty queue on an asset that has been live for a year is hardened code; the same empty queue on a program listed in the last six weeks is simply unexamined, because nobody has had time to file against it. Sort the two apart with the listing date and the accepted-report count together, and when a fresh listing is also forkable and small, work it first: a two-day-old program with a modest floor is a better use of a night than a well-known asset whose every component already carries an accepted report.

**Prefer surfaces with nothing between the attacker and the payoff.** In descending order, because each step up adds a layer that can absorb the bug: browser extension, desktop or IDE plugin, mobile app, a service you compile and run yourself, a vendor-hosted instance, multi-tenant SaaS. The first three run on the victim's machine, where the attacker is simply a page or a co-installed app and no proxy sanitises the answer; by the time you reach a hosted instance the vendor's edge can refuse the request and its API can redact the value. Three targets in a single night died on exactly that ladder — an edge 403, a redacted secret, and a documented design trade — while the code defect was real every time.

Rule of thumb: a small program with 10-20 awarded reporters and 95%+ efficiency beats a famous program with 300.

## Phase 1 — Get the real scope (proven, no login needed)

HackerOne exposes public structured scopes over GraphQL, no auth:

```python
import urllib.request, json
Q = '''query($h:String!,$f:Int!){team(handle:$h){name submission_state offers_bounties
structured_scopes(first:$f,archived:false){edges{node{asset_identifier asset_type
eligible_for_bounty eligible_for_submission max_severity instruction}}}}}'''
req = urllib.request.Request('https://hackerone.com/graphql',
    data=json.dumps({'query': Q, 'variables': {'h': 'PROGRAM_HANDLE', 'f': 200}}).encode(),
    headers={'Content-Type': 'application/json', 'Accept': 'application/json',
             'User-Agent': 'Mozilla/5.0 (Windows NT 10.0; Win64; x64) Chrome/131.0'})
print(json.load(urllib.request.urlopen(req, timeout=60)))
```

- `curl` from git-bash silently returns nothing on this endpoint — use Python `urllib`.
- Fields that do not exist on `team` (e.g. `bounty_total`) 400 the whole query; start minimal and add fields one at a time.
- Bounty ranges and policy text are not in GraphQL: fetch `https://hackerone.com/<handle>` with `web_extract`.
- `eligible_for_bounty=false` assets are VDP-only: testable but unpaid. Do not spend agent time there while a bounty asset exists.

## Phase 3 — Vuln matrix (what actually pays)

Anything whose whole impact is "this exposes information" is a Core Ineligible Finding until something is done with it. The pays / does-not-pay shape table is in `references/hackerone-platform.md`; consult it before spending an agent on a class, not after a triager rejects the report.

- **Auth**: OTP/2FA bypass, reset-token predictability, session fixation, JWT alg confusion, OAuth `redirect_uri` validation, login CSRF.
- **Authz**: IDOR on numeric/UUID object ids, tenant isolation, role escalation, GraphQL field-level authz gaps.
- **Injection**: SQLi, command injection, SSTI, XXE, deserialization — only with a working payload and visible impact.
- **SSRF**: only with a demonstrated reachable internal target or metadata service.
- **Business logic**: price/quantity/discount manipulation, coupon reuse, race conditions (double-spend, duplicate redeem). Highest payouts, lowest dupe rate, needs a real flow — ask the user before creating accounts.
- **Crypto/consensus (chains)**: reachable panic/DoS, signature verification gaps, quorum math, replay protection, key handling. A finding that only lands once a privileged EOA or operator key is compromised is a design observation, not a vulnerability: "requires key theft" is the answer it gets. One EOA holding mint, freeze and upgrade rights, or a bridge that accepts a caller-supplied source-chain tuple from a trusted role, is a hardening note — write it to the user, not to the program. The class that pays is an **unauthenticated** caller reaching a write or a privileged read. Verifying either against live chain state takes two minutes; recipe in `references/smart-contract-triage.md`.
- **Biometric / liveness / KYC SDKs**: decide which side owns the verdict before designing an attack. Decompile the SDK and read the request builder: if the client uploads only media, params and a type, and every verdict field you inject is ignored, the server scores independently and "make the client say live" is dead on arrival. The remaining surface is the media input (URLs, ids, replay of a captured frame) and the token minting path. Establish authority first; bypass techniques second.

## Phase 4 — Evidence standard

**Information disclosure alone is a Core Ineligible Finding and pays nothing.** Version banners, config manifests, exposed API docs, peer lists and node status are all in the same bucket: the triager will close them as "information disclosure without demonstrated exploitation" and no rebuttal survives, because the follow-on step is usually a DoS, which programs exclude. Only three shapes pay: access-control bypass where you actually received someone else's data, authentication bypass, and a working exploit chain with a visible impact. Do not spend agent-hours producing exposures.

A finding is real only when you can paste:
1. The exact request (method, URL, headers, body).
2. The exact response (status + the relevant bytes, not a description).
3. Why that response is wrong (what should have happened).
4. The impact in one sentence a non-engineer triager understands.

Anything short of that is a **HYPOTHESIS** and must be labelled as such. Never let an agent's summary upgrade a hypothesis into a finding.

**Reproducing without the vendor's tooling.** A gRPC method with an empty request needs no `.proto` and no `grpcurl`: open a channel and call it raw — `ch.unary_unary('/pkg.Service/Method', request_serializer=lambda x: x, response_deserializer=lambda x: x)(b'')` — then read the bytes and pull strings out of the response. For a source-code finding, the reproduction is a committed test in the repo's own harness; the report quotes the test name and the command that runs it. A code path you only read stays a HYPOTHESIS however convincing the argument, and saying so is what keeps the report credible.

**Execute the claim before you submit it, and read the whole function rather than the lines you cited.** A static read is how a convincing false positive is born: spot a loop, spot a state variable that looks like it is never updated, write the defect up, and be wrong because the update sits three lines above the `for` or inside the increment you skipped. Static claims about what a function produces at runtime are HYPOTHESIS no matter how clean the argument; the finding becomes reportable when a harness prints the wrong output. When the repo will not build on your host, extract the function body verbatim (`sed -n 'A,Bp'` into an `.inc`, then include it) and compile it against shims so the code under test stays byte-identical and a second agent can diff it back — but treat a shim-built harness as unverified until someone confirms the shim did not fabricate an input a real caller cannot send. Recipe: `references/local-build-and-run.md`. A harness is itself a claim and can be wrong in ways that read exactly like proof; the recurring shapes and the one-line check for each are in `references/harness-honesty.md`.

**For a library or SDK, ask who can mint the input before asking what the bug does.** The equivalent of "untrusted caller" in an application is "input a party without the capability can produce" in a library, and most convincing-looking SDK findings die on that question. A key-derivation collision where two secrets fold to the same bytes is a real defect and worthless, because the only party who can present the colliding secret already holds the client credential it protects; a token carrying a malformed claim is worthless when only the trusted issuer could mint it; an overload only the integrating application can call is worthless when the SDK's public entry point never reaches it. Name the party in production who can supply that exact input without already holding the capability the bug would grant. If the answer is the issuer, the client, or the application itself, the finding is a hardening note however clean the test.

**Check the payoff against a second control before spending agents on the defect.** A defect can be real, executed, and still worthless because the value it exposes is already masked one layer up: an API that returns `"<redacted>"` unless a privileged query parameter is passed, a framework that scopes every query to the tenant, a gateway that strips the header before the app sees it. Make one live call and read the actual response shape before building a theory around the value. An operator that adopted another project's service user and wrote its password into a Kubernetes secret was writing the literal string `<redacted>`, because the vendor's API redacts by default and the SDK passes no `include_secrets` parameter — one request would have killed that lead before eight agents were dispatched, and it is the cheapest question in any credential-disclosure hypothesis: open the endpoint yourself and look at the field.

**"The product claims X but never does X" is the strongest source-code finding, and its proof is a caller count.** Once you find that a documented action only writes a flag, locate the function that would perform the real work and establish whether anything calls it: `grep -rn "<function_name>"` over the tree, then the management-command registry, the cron and systemd units, and the imports. A cleanup or deletion routine that exists with zero callers is what turns "the cleanup is deferred" from a hardening note into a verified inconsistency, because the code that would keep the promise is present and orphaned. Quote the definition line, then state plainly that the call graph has no edge into it.

## Phase 3.5 — the hypothesis gate (before any hunter is dispatched)

A hunter told to "audit the authz" burns 25 minutes to return "no missing check found". A hunter told "make an ordinary namespace user obtain another project's credential" keeps working until it succeeds or names the line that makes it impossible. The gate is what turns a vague vector into one of those two briefs — or kills it in three minutes.

Every vector must be stated in four lines before it gets an agent:

    SALDIRGAN:    who, with what permission
    KANIT:        file:line, and which fresh code makes it live
    KAZANÇ:       exactly what they obtain
    İMKANSIZLIK:  the single most likely sentence that kills this claim

Acceptance rule: the gain has to be another party's data, identity or money. A gain that is an error message, a revert, self-harm, or "an admin could already do it" fails the gate and the vector is dropped without spending a slot. Applying this gate costs three minutes of reading; skipping it costs eight agents and half an hour, which is how a night produces zero findings and twelve dead claims.

Score the survivors on how cheaply they can be executed, take the top five, and only then dispatch. The `İMKANSIZLIK` line becomes the first thing the refuters test — if they cannot answer it, the claim is not ready.

## Phase 4 — Offensive tasking (give the agent a goal, not a checklist)

A hunter told to "check whether the handler validates membership" finds that it does, and stops. A hunter told to "make an ordinary user's action execute with the admin's token" keeps working until it succeeds or proves it cannot. Brief the objective and the attacker, never the bug class.

Seven framings that keep producing leads where a checklist produces negatives:

1. **Mine the fresh commits — but only after you know who else is watching them.** Anything merged in the last 90 days is the least-exercised code in the tree: `git log --since=90.days --oneline`, then read every merge that adds a feature, a fallback, a retry or a new integration. A fallback is a privilege decision: one commit made a user's action fall back to an admin token when the user's own token was rejected, a confused deputy by construction that no checklist would have asked for. **The catch is that the vendor's recent fixes are the most crowded place in the repo**, because every hunter who watches the project reads the same commits. The best finding to come out of this method — an unvalidated `build_id` write reached by no `validateBuild` caller — came back a duplicate. So before mining, build the coverage map: read `/crowdstream.json` and the recent accepted components, then prefer a corner the fixes did *not* touch (legacy modules, admin and internal endpoints, importers, migration scripts, deprecated routes still mapped, the second language in a mostly-Java tree). Fresh commits tell you the class is live; the coverage map tells you which instance nobody has taken. **And the untaken instance is usually a sibling field.** When a vendor patches a missing check for one field — a mass-assignment or immutable-field bug — the same class survives on the fields nobody patched: grep the resource layer for every handler that writes a request value into a row, then compare that set against the fields the handler's own comment or DTO says the caller may change. The comment is the specification and the code is the bug, which is why the pair is worth more than either the commit history or the coverage map alone.
2. **Trust-boundary diffing.** Find two components that disagree about identity or permission: a platform user id versus an external account, a plugin admin token versus a user token, a tenant id passed in a body versus taken from a session. The bug is where the two disagree.
3. **State-machine abuse.** Connect then disconnect, subscribe then unsubscribe, invite then remove, delete the object then recreate the id, cancel mid-flight. Look for state that survives the transition: subscriptions, tokens, caches, public links, webhooks.
4. **Make the happy path fail on purpose.** Revoke the token, break the external URL, return 500, expire the session, remove the permission — then watch what fallback, retry or default kicks in. Fallbacks are where privilege leaks.
5. **Chain two legitimate features.** Each is documented and safe alone. Ask what happens when feature A's output is feature B's input, especially when A produces an id, a URL or a token that B trusts.
6. **Differential identities.** Send the same request as admin, as an ordinary member, as a guest, and as an outsider. Any difference in response shape, not just status, is a lead: extra fields, different error text, timing that reveals existence.
7. **Parse what nobody parses.** Webhook bodies, JQL and search strings, CSV imports, markdown renderers, avatar and emoji uploads. Find an input the code accepts from a lower-privileged user that reaches a parser written for trusted data.

Teach each hunter its attacker in one sentence — "you are a member of team A with no admin rights and a laptop" — and require the final answer to be either a running exploit or a specific, named reason it is impossible. "No missing check found" is not an answer the brief accepts.

## Phase 5 — Report shape

**"Nothing calls this function" is a claim you must prove with an unfiltered search.** A search whose output you truncated is not evidence of absence: one run cut off before `scripts/source_deleter`, which turned a live systemd daemon into "dead code" and nearly put a false claim in front of a triager. Search by the symbol name with no `head`, and also search the places a call hides: `scripts/`, `bin/`, `debian/*/systemd/`, `install_files/`, `molecule/`, `cron.d/`, Dockerfiles and entrypoints. If the target ships an init unit, a test that asserts the unit exists is proof the path is live.

**Prove impact through the target's own call sites, not through an imagined integrator.** Triage rebuts an uninitialised-output, missing-check or unchecked-input finding by checking whether any caller in the tree actually reaches the bad value. Fireblocks closed exactly this way: "every caller in the library handles the empty path itself and never reads the unwritten output." Before writing, grep the repo for the consumers of the function and show the impact at one of them; if every consumer guards, the finding is hardening and P5. This rule applies to any library-shaped target, and it is the single most common reason a technically true report pays nothing.

**On Bugcrowd, the VRT category you pick sets the suggested priority, and triagers usually leave it alone.** The submission form shows the priority a category maps to before you submit. If it shows P5 for a finding you believe is P4, pick a different category or `Other` and argue the priority yourself in the description; never submit with a P5 mapping and hope the triager upgrades it. A P5 pays nothing and earns no points, however good the underlying bug is. VRT selection stays editable while the submission is in `New`, so a bad mapping can still be fixed before triage closes. **Some classes have no node at all** — mass assignment, compliance-control bypass, a field the API accepts that the comment says is immutable. There is no `mass assignment` entry in 1.19.1, and `Application-Level DoS > App Crash` carries only mobile variants at P5 with no native counterpart. In that case pick the nearest node that does carry a paying priority (a modify-by-identifier IDOR for a field the caller should not be able to write), select it, and argue the real class in the description rather than picking an evocative node that maps to nothing.

**When a later pass proves a submitted report wrong, say so the same day and withdraw it.** Accuracy is what lifts the new-account submission cap, so a report you now know to be false costs more than the slot it used; the honest correction is also the only thing that keeps the user's trust in every other verdict you gave. Withdraw through the submission's own page, tell the user plainly which claim failed and which agent's evidence killed it, and fold the cause into the next round's briefs.

**Order a batch by acceptance probability, not by payout.** When several reports are ready and the platform caps how many go out, the user's money is maximised by sending the ones most likely to be paid. Acceptance probability is not severity: a defect whose behaviour you have executed and can show in a terminal paste (a cleanup routine with zero callers, a count that cannot match the code that writes it, a committed test that fails) needs no attacker model and is hard to argue away, while a higher-paying finding whose report depends on the triager accepting an attacker model is the one that dies. State the order and a one-line reason per report.

Present that order as one numbered list — position, program, one-line finding, payout band — strongest first. Do not group it by program and do not answer with a matrix: the user is deciding what to paste into which form, and the moment they have to reconstruct the sequence themselves they will ask which one goes first. When they say they are confused, drop everything except the first item.

```
Title: <vuln class> on <asset> leads to <impact>
Affected asset: <exact in-scope identifier>
Summary: 2-3 sentences, impact first.
Steps to reproduce: numbered, copy-pasteable, includes the account/role used.
Impact: what an attacker gains, quantified.
Remediation: one concrete fix.
Supporting: video/screenshot if the program requires it.
```

Many programs require a **recorded video** — check the policy before promising a report.

Two things never go in a report: the bounty amount (it reframes the finding as motivated) and a deference clause ("if this is intentional I would rather hear that"). The second reads as an invitation to close as Not Applicable. State the finding, state its limit once, stop.

For a source-code finding, every hop in the argument needs a `file:line`: config value, the function that consumes it, and the branch that decides. **Copy the component path and package out of the tree with `find . -name <File>.java` before writing the report**, never from the module name you remember: a class in `teletraan.resource` written up as `deployservice.handler` is one click from a triager deciding the rest of the evidence was not checked either. Then state the deployment dependency explicitly ("reachability depends on the security group, which is not in the repository"). Naming the limit yourself is what keeps a real finding at Medium instead of watching a triager drop it to Informational for you.

## Pitfalls
- **A program that publishes a known-issues repo has already answered your dedupe, and that repo is the eligibility boundary.** Before dispatching hunters on a source-code target, clone `Metricxyz/Known_issues`-style repositories and read the program page's audit table: audits, acknowledged-but-unfixed findings, and "fix pending" rows are all ineligible by root cause, so a hunter that finds one has burned the slot. Two corroborating checks make a kill defensible — grep the repo's own tests for one that asserts the behaviour (a test that asserts it means intended), and diff the published `audit-<commit>` tags when the public history is squashed, because the tags are the only record of what a fix changed.
- **A managed challenge is bot detection, and a human beats it once.** Automated browsers get challenged on CDP / `navigator.webdriver` signals regardless of how clean the IP is, so "it is blocked" usually means "this client is blocked". A visible Chrome that the user solves once keeps the `cf_clearance` cookie, and that cookie plus the exact same UA replays from `curl_cffi` for the rest of the session. Procedure and gotchas: `references/waf-walled-targets.md`. Only pivot to mobile/source-code assets if the user cannot reach a browser at all. **Volume burns the address too.** A burst of roughly fifteen requests at one per second took a host from serving the application to challenging every request, and once challenged that address is spent for the session — probe with a handful, keep sweeps polite, and when a host answers a block page on every path check `/cdn-cgi/trace`, because a uniform block is an allowlist or a country filter rather than a challenge, and no cookie will fix it.
- **APK mirrors are mostly dead**; the one that works is documented in `references/mobile-apk-analysis.md`.
- **jadx needs a 64-bit JDK 11+.** This host's `java` is a 32-bit JRE 1.8 that dies with `The specified size exceeds the maximum representable size` when the launcher passes `-Xmx4g`.
- **`git clone` of a huge repo inside an agent burns its whole budget.** Use `--depth 1` and name the directories that matter.
- **Dedup belongs in target selection, not in report writing.** Scanning a report feed just before submitting buys little: a duplicate can cite an undisclosed report you could never see, and only the first valid report wins. But the same information decides which *asset* to work, and there the cost of not looking is a wasted night. On Bugcrowd the data is machine-readable logged out — `/engagements/<code>/crowdstream.json` and `/statistics` — so before committing agents, check whether the specific component you intend to attack has had an accepted report in the last few months. An asset with an empty queue next to a busy asset on the same program is the signal worth acting on; it is also the difference between "nobody looked" and "everybody tried and found nothing", which you can only tell from the reward history. Rank the class that is already farmed last, and do not re-check hacktivity per report once the asset is chosen.
- **For source-code work, depth beats headcount.** Sixteen agents on twenty-five-minute passes over a monorepo come back with "clean" without having read anything twice, and swarm-sized batches mostly reproduce each other. The shape that works is one target, two to four agents, a long per-agent budget, and an explicit rule that each writes findings to disk as it goes so an interruption costs a paragraph instead of the pass. Split by module or asset, never by "one agent per idea".
- **State the per-agent budget as a ceiling, not a target.** "You have six hours" produces padding; "up to six hours, return as soon as the report is written" produces a finished pass in the time the work actually needs. Agents given a floor will sit on the clock, and a mid-run correction from "at least N hours" to "N hours is the cap" is a correction the user should not have to make twice.
- **A "full hack scenario" program is not worth entering** unless you already have a chain — partial findings get closed unpaid.
- **405 on every method means the path is wrong, not that the endpoint is hardened.** Routers are case- and slash-sensitive: `/createprocess` 405'd while `/createProcess` returned 400 and was the live handler. Before concluding a route is dead, try case variants, trailing slash, and a version prefix. A 405 with no `Allow` header is the tell that you never reached a handler.
- **On a vendor-hosted instance, find out whether the edge or the application answered.** A defect can be real in the source and still unreachable on the in-scope asset, because the vendor's proxy refuses the request before the app sees it. Run a three-way matrix that varies the identity and the parameter independently (attacker without the permission, attacker with it, privileged account with the refused value), then classify each response: `server: cloudflare` with an HTML body and a vendor redirect page is the edge; a JSON error with an `api.`-style id is the app; a 500 only for the privileged row means the handler ran and the parameter was accepted. If the edge is what stops the attacker, stop there — a bug in a repository that is not itself an in-scope target pays nothing when the deployed asset mitigates it. Provisioning, the authenticated-session recipe and the API quirks that make these probes valid: `references/hosted-instance-testing.md`.
- **A handler registered without the auth middleware is not an unauthenticated endpoint.** Route tables that show one handler wrapped in the auth wrapper and its neighbour bare look like an open door, and the claim collapses the moment you check the host platform: Mattermost's server deletes any client-supplied `Mattermost-User-Id` header and sets it from a validated session before the plugin sees the request, so those "open" routes were closed and the finding was nothing. Before writing "unauthenticated", establish two things — what the platform's proxy does with the identity header, and whether the handler validates it itself (a shared `decodeRequest` that rejects a missing or forged id is authentication, wherever it lives). Test the route with no session at all; absence of middleware is a hint, not evidence.
- **A permissive configuration is not a vulnerability until something exercises the permission.** A trust file that grants an app a capability, a config that turns a protection off, a default that allows more than it should — each is a fact, and triagers answer facts with Not Applicable. N/A costs more Signal than Informational and invites the reply "show us a practical exploitation scenario". The bar is a request that demonstrates the permission in use, or a code path that proves it is reachable from an attacker. When you cannot show that, do not spend the report: hand the user a hardening note instead and keep hunting.
- **A defect reachable only by the caller passing a bad argument is P5.** A NULL pointer that crashes when the API is handed NULL, a zero-length input that leaves an out-parameter unwritten, an unchecked length on a buffer the caller allocated: all real coding errors, all rated informational, because the caller is already trusted. Triage reads them as API misuse, not a vulnerability, and the same is true of anything whose precondition is "the integrating application must do something careless". Rank that class last, or hand the maintainers a patch and keep hunting for the shape where an untrusted party supplies the input. **The same verdict comes back when the caller is an untrusted party that already holds the capability the bug would grant.** An argument reaching a shell is not a finding when the only sender is the trusted server, which can already run arbitrary code through another field on the same message; a path traversal is not a finding when the destination is a directory the same caller chose. Before writing, finish this sentence: "this bug lets <party> do <thing> that they could not already do." If the answer is a capability they already have, the report is a hardening note. **The exception is a vetting control the same principal cannot switch off.** When the defect lets a deployer install an artifact that the deploy API itself refuses — a private build on a stage whose `allow_private_build` is derived from stage type and cannot be flipped, a non-SOX artifact on a stage whose `is_sox` is pinned — the gain is not the deploy permission they already hold but the bypass of the checks that keep them to vetted origins. Say it in that shape, and say it about the shipped authorization mode rather than about what a real employee holds, because the vendor's own policy layer usually lives outside the repository.
- **A reproduced behaviour that the code and the docs specify is a feature, and reproducing it proves nothing.** One finding was a genuine primitive — an order hash that covers only the original consideration items, so a fulfiller can append more — verified with a passing fork test and real balances. It was still worthless, because the function's own comment and the protocol documentation both name the mechanism as the tip and referral path, the appended item is funded by `msg.sender`, and the maker receives exactly the price they signed. Before writing up an omission, grep the typehash comments, the interface docstrings and `docs/` for the behaviour you think is missing: `hash omits X` is a finding only when X is not the documented extension point. Pair this with one question the pitfall above does not ask — **who funds it?** If the only wallet that loses is the caller's, no third party was harmed and no triager will read it as a vulnerability.
- **A version/build manifest in a response header is a Core Ineligible Finding.** A leaked module inventory (`kyc`, `pms`, `promo`, …) reads like a Medium to a fresh agent and pays $0. Check the exclusion list before letting an agent label it.

## Reporting to the user
Per target: what was tested, what is verified, what is blocked and why. Never inflate a hypothesis into a finding, and never call a bounty earned until the program pays it.

- **Open with the verdict, in the first line.** If nothing is submittable, say "nothing submittable yet" before the detail — the user is deciding whether to spend a report, and a buried negative wastes their time.
- **A verified finding goes in CAPS, alone, at the top.** This user asked for exactly that: when something is confirmed and reportable, it is the whole message, not a bullet inside a status digest.
- **A scheduled status digest is not your report.** If a cron job already posted progress, still give your own assessment: which claims you re-ran yourself, which severity labels you are overriding, what died. Silence after an automated digest reads as you having nothing to add.
- **Rank every recommendation by time-to-money.** The user optimises for "fastest thing that converts to a payout", not for the highest theoretical severity. Say plainly when a program is a wall and when the remaining money is behind a login.
- **Never ask whether to stop for the day, and never offer a menu of "shall we continue" options.** This user decides when the run ends; a check-in question reads as stalling and gets answered with irritation. When a round produces nothing, state the result, the one thing it taught, and start the next round — or wait to be told. The same applies to rhetorical options: give the recommendation, not a choose-your-own-adventure list.
- **Label confidence by evidence type, in those words.** "Executed, here is the output" and "read from the code, would need a run to confirm" are different claims, and the user is choosing what to stake a submission slot on. Never call a finding the strongest or most promising off a static read: the one described as the cleanest evidence of the night — verified by the repository's own test, no less — turned out to be flatly wrong when someone built it. If you have not run it, say you have not run it, in the same sentence as the ranking.

- **Deliver a submission-ready report as a humanized `.txt` on the Desktop.** When the user asks for "the report", they mean a file they can paste into HackerOne, not a chat summary: plain text, no markdown bold, evidence (request, response, hashes, `file:line`) left byte-exact, prose rewritten for voice. Save it to the Desktop and name the path. Keep the severity you can defend, not the one that flatters the finding.

**Fetch every link inside the report before delivering it.** A dead link in the evidence section costs the triager's trust exactly where the report is strongest. Two link shapes break silently: a platform program URL is `/engagements/<code>` on Bugcrowd, not `/<code>`, and a GitHub `blob/<branch>/<path>` URL is only valid on that repository's real default branch, which is frequently not `main`. When a link 404s, read the branch from the repository API rather than guessing, and note the branch at the end of the link block so the next person does not repeat it.

**Re-test the top candidate yourself before recommending a submission.** A child's severity label is a guess made without the exclusion list in front of it. Re-run the request, confirm the asset is bounty-eligible, and confirm the class is not on the Core Ineligible list. Confirm the single load-bearing fact rather than re-reading the finding — the caller count, the check that is or is not in the path — because that one fact is what the whole report rests on, and it is the fact a child is most likely to have inferred. Killing a lead the user was about to submit is worth more than finding another Low.
